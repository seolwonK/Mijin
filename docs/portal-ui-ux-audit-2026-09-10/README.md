## 판단

**기본 업무는 처리할 수 있지만, 현장에서 빠르게 판단하고 오류에서 복구하는 경험은 개선이 필요하다.** 디자인은 큰 인사 배너·반복 통계·둥근 카드·강한 그림자가 비슷한 비중으로 쌓여 있다. 지금 해야 할 일과 참고 정보의 차이가 작다. 특히 기사 모바일 화면은 근로확인서 안내까지 더해져 첫 배정의 전체 내용을 보려면 스크롤해야 한다.

새 장식을 더하기보다 **대기 배정 → 진행 중 작업 → 참고 정보** 순서로 화면을 정리하는 것이 우선이다. 디자인 외에도 실제 진행 건 누락, 오류를 빈 데이터로 표시하는 문제, 회수 상태 오표시를 재현했다. 이 항목들은 함께 수정해야 화면을 신뢰할 수 있다.

- [기능별 체크리스트 154개](CHECKLIST.md): **통과 81 · 개선 44 · 소스 확인 20 · 미검증 9**. 개선 44행은 아래 **18개 개선 과제**로 묶었다. 같은 결함이 여러 역할·기능에 나타나므로 44개의 독립 버그라는 뜻은 아니다.
- **10개 화면 × 4개 폭**을 확인하고, 오류·상태·경계값 증거를 포함해 **스크린샷 68장**을 남겼다. 폭은 320 / 390 / 768 / 1440 CSS px, 기본 높이는 844px이다.
- 기존 기능 테스트 **98개 시나리오**는 빌드 실행본에서 92개 통과 후 환경을 보정해 나머지 6개도 재검증 통과했다. 알 관련 DB 테스트는 **9/9 통과**했다. 테스트 실행 조건과 수정한 테스트 기준은 아래에 공개했다.
- 실제 KCP/PASS 인증, 실문자 수신, 전화·지도 앱 전환, 실기기 키보드·알림·Safari·스크린리더는 **미검증**이다. 뷰포트·모의 인증 검증을 실기기 검증으로 간주하지 않았다.

## 문제별 상세와 수정 후 검증 조건

### F01 — 홈의 정보 순서를 업무 중심으로 바꾸기

**관찰:** 390×844px에서 응답 대기 제목은 업체 y=497px, 기사 y=667px에 나타났다. 인사 배너 자체가 모바일 112px이고, 통계 요약과 알 카드가 뒤따른다. 기사 화면의 대기 카드는 첫 화면 아래로 이어진다. 업체는 첫 카드가 보이지만 화면 상단의 큰 비중을 참고 정보가 차지한다. 대기 목록에는 자동 회수까지 남은 시간이 없고 상세에 들어가야 확인할 수 있다.

**개선:** 인사 배너를 없애고 작은 “오늘 배정” 제목과 갱신 상태로 대체한다. 미서명 기사에게는 서명 안내를 최상단에, 배정을 받을 수 있는 사용자에게는 응답 대기를 먼저 배치한다. 대기 카드에 긴급도·남은 응답 시간·주소·고장 요약을 우선 표시한다. 진행 중 작업 뒤에 알·성과·정산을 둔다. 서명 상태와 업무 상황에 따라 순서를 달리하면 자연스럽다.

**수정 후 확인:** 390×844px에서 첫 대기 카드의 핵심 내용과 상세 진입이 스크롤 없이 보이고, 320px에서도 시간·주소가 잘리지 않는지 확인한다.

### F02 — 진행 중인 작업을 최근 이력 제한에서 분리하기

**재현:** 본인에게 수락·출동 중 작업 2건을 둔 뒤 더 최근의 완료 배정 100건을 생성했다. 두 역할 모두 목록 API는 100건을 반환했고, 오래된 진행 중 배정 ID는 포함하지 않았다. DB에는 진행 건이 그대로 남아 있었다.

**원인:** 상태와 무관하게 `createdAt desc`, `take: 100`으로 가져온 뒤 브라우저에서 대기·진행·과거로 분류한다. “전체 보기”도 이미 잘린 목록 안에서만 펼친다.

**개선:** 대기·진행은 제한 없이 별도 조회하고, 과거 내역에 커서 페이지 이동을 적용한다. 검색·필터를 추가할 경우에도 현재 작업이 필터나 이력 제한 때문에 사라지지 않게 한다.

**수정 후 확인:** 완료 이력이 101건 이상이어도 모든 대기·진행 건이 보이고, 과거 100건 이후도 가져올 수 있어야 한다.

### F03 — 로딩·오류·빈 화면을 따로 표시하기

**재현:** 목록에 503을 주면 “요청 실패 (503)”과 “새로 배정된 건이 없습니다”가 함께 나타난다. 추천·후기 API가 실패하면 각각 “아직 추천한 업체·전기기사가 없습니다”, “아직 받은 후기가 없습니다”로 표시된다. 최초 로딩에서도 같은 문구가 잠깐 보인다. 통계·알은 대시로 남고, 기사 계약 안내는 계속 로딩 모양을 유지한다.

**개선:** 각 영역에 로딩 / 정상 데이터 / 정상 0건 / 실패 상태를 둔다. 기존 데이터가 있다면 유지하면서 “최신 내용을 가져오지 못했습니다”와 확인 시각·재시도를 표시한다. 계약 조회 실패는 서명 필요 여부와 구분한다. 업체에도 직접 새로고침을 제공한다. 기사 새로고침은 현재 배정 목록만 갱신하므로, 다른 카드의 갱신 범위도 명확히 한다.

**수정 후 확인:** 성공한 빈 배열에서만 “없음”이 나오고, 실패한 영역에는 이유와 다시 시도할 방법이 있어야 한다. 나머지 정상 영역의 사용은 유지한다.

### F04 — 상세의 일시적 오류가 현장 정보를 지우지 않게 하기

**재현:** 정상 상세를 연 뒤 다음 상세 폴링에만 503을 반환했다. 8초 뒤 고객 전화·주소·고장 설명·처리 버튼이 모두 사라지고 오류 문장만 남았다. 직접 재시도 버튼은 없고 다음 자동 갱신을 기다려야 한다. 없는 건도 “요청 실패 (404)” 위주로 안내한다.

**원인:** 데이터가 이미 있어도 `if (error || !job)` 분기로 전체 본문을 교체한다.

**개선:** 마지막으로 받은 상세와 전화·주소를 보존하고 갱신 실패 안내를 추가한다. 변경 작업은 최신 상태 재검증을 거치며, 안전하게 실행할 수 없으면 이유를 설명한다. 404에는 “배정이 종료되었거나 접근할 수 없습니다”와 목록 이동을 제공한다.

**수정 후 확인:** 폴링 실패에도 고객 연락처가 유지되고, 재시도로 회복되며, 상태 변경 충돌은 409로 안내한다.

### F05 — 금액 길이에 견디는 요약 만들기

**재현:** 대기 12,345,678원, 지급 완료 123,456,789원을 넣자 상단 3열 숫자가 서로 겹쳤다. 문서 폭이 390px에서 428px로 늘어났다. 아래 수수료 요약에서도 ‘원’이 다음 줄로 떨어진다.

### F06 — “나의 배정 상태”와 “접수 전체 상태” 구분하기

**재현:** 배정 상태가 EXPIRED이고 접수가 RECEIVED이면 목록과 상세에는 “배정대기”가 표시된다. 상세에 회수되었다는 설명이 없다. 거절된 건도 목록에서는 접수 상태로 보이고 상세에 들어가야 거절 사유를 알 수 있다.

**개선:** 주 상태는 “응답 기한 만료”, “거절”, “배정 취소”처럼 현재 사용자와의 관계를 표시한다. 필요하면 접수 전체 진행 상태는 보조 정보로 둔다. 회수 시각·사유·다음 행동을 안내하고 완료·종료된 배정의 행동 버튼은 계속 제한한다.

**수정 후 확인:** REQUESTED / ACCEPTED / REJECTED / EXPIRED / CANCELED와 접수 상태 조합을 각각 확인한다. 종료된 건을 사용자가 아직 대기해야 하는 업무로 이해하지 않아야 한다.

**수정 후 확인:** 비밀번호 불일치·증빙 누락·인증 누락·전화 오류를 모바일 긴 폼에서 각각 재현하고, 사용자가 문제 위치로 바로 돌아갈 수 있어야 한다.

| 순서 | 업체 | 전기기사 |
| --- | --- | --- |
| 상단 | 업체명·영업 상태·내 정보 | 기사명·배정 가능 상태·내 정보/지원 |
| 첫 영역 | 응답 대기 건수·마감·우선 처리 카드 | 미서명일 때 서명 안내, 서명 완료 시 응답 대기 |
| 다음 | 진행 중 작업, 전화·길찾기·현재 단계 | 진행 중 작업, 전화·길찾기·현재 단계 |
| 참고 정보 | 알 잔액·충전 문의, 성과·정산 요약 | 알 잔액·충전 문의, 성과·정산 요약 |
| 별도 보기/접기 | 지난 내역·정산 전체·추천·후기 | 지난 내역·정산 전체·추천·후기 |

모바일 하단 내비게이션을 추가한다면 실제로 자주 이동하는 목적지만 넣는다. 현재 긴 홈을 그대로 두고 탭 모양만 추가하기보다 배정·내역·내 정보 등 화면 분리를 먼저 정하는 편이 낫다. 사용자 수익과 알 순위는 중요한 정보지만 수락 제한시간이 있는 작업보다 먼저 차지할 이유는 적다.

권장 구현 순서는 **진행 건 누락/오류 상태/상태명 → 모바일 정보 배치/금액/대비 → 폼·키보드·사진 모달 → 정산·계정 관리 동선**이다. 근로확인서 조건 공개는 첫 단계와 함께 처리한다.

## 판단 기준

- 화면 폭: [W3C Reflow 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)의 320 CSS px 기준을 참고했다. 본 감사는 모든 확대 모드·기기에서의 전체 준수 검증은 아니다.
- 글자 대비: [W3C Contrast Minimum 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)에 따라 일반 글자의 4.5:1 기준과 실측 사례를 비교했다.
- 조작 크기: [W3C Target Size Minimum 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)의 24px·예외 규정과 현장 모바일 조작을 위한 본 감사의 44px 권고를 구분했다.
- 모달: [WAI-ARIA Dialog Modal 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)의 포커스 이동·내부 순환·닫은 후 복귀를 기준으로 확인했다.
