# 만족도 설문 내부 점검 및 알 충전 개선

점검일: 2026-09-10. 개발 DB와 분리한 로컬 테스트 DB, `http://localhost:3001`에서 검증했다. 실제 문자 발송은 하지 않았다.

후속 변경: 전체 설문 조회·상태 필터·고객 입력 금액·페이지 이동·모바일 목록을 추가했다. 아래 관리자 기능 표는 개선 전 점검 기록이며, 현재 동작은 [설문 목록 개선 기록](./SURVEY-LIST.md)을 참고한다.

## 설문 링크 검증 결과

| 확인 항목 | 결과 | 검증 방법 |
| --- | --- | --- |
| 업체의 출동 중 건 완료 처리 | 통과 | 실제 상태 변경 API 호출 후 설문·문자 로그 생성 확인 |
| 개인기사의 출동 중 건 완료 처리 | 통과 | 업체와 동일한 독립 시나리오 |

| 내부 발송 함수를 다시 호출했을 때 | 통과 | 설문·토큰 재사용. 관리자 재발송 UI가 있다는 뜻은 아님 |
| 실제 Solapi 접수·통신사 전달·휴대폰 수신 | 미검증 | 실문자 발송을 실행하지 않음 |

근거 테스트: `tests/customer/survey-lifecycle.spec.ts`, `tests/customer/lookup-survey-api.spec.ts`, `src/lib/__tests__/survey-delivery.db.test.ts`.

링크의 주소는 `APP_BASE_URL` → 완료 처리 요청의 origin → `http://localhost:3000` 순서로 정해진다. 현재 로컬 `.env`에는 APP_BASE_URL이 없으며, 내부 테스트 링크는 localhost:3001로 생성됐다. 외부 고객에게 발송할 때에는 실제 공개 서비스 주소를 APP_BASE_URL로 지정하고 해당 주소의 접속도 확인해야 한다. 운영 서버 환경변수는 이번 점검 대상이 아니다.

## 관리자 기능의 현재 범위와 누락

관리자 경로: `/admin/analytics/surveys` (분석 → 설문).

| 기능 | 현재 상태 |
| --- | --- |
| 응답률·미응답 수·고객 입력 금액 통계 | 있음 |
| 미응답 고객 접수번호·이름·전화번호·경과일 조회 | 있음 |
| 전화 연결 | 있음 (`tel:` 링크) |
| 접수 상세의 설문 상태·제출 내용 확인 | 있음 (`/admin/requests/[id]`) |
| 문자 발송 성공·실패·실패 사유 확인 | 관리자 UI 없음. DB SmsLog에만 기록 |
| 문자를 못 받은 고객과 받은 뒤 미응답인 고객 구분 | 없음 |
| 개별 설문 문자 재발송·재시도 | 없음 |
| 관리자 설문 링크 복사 | 없음 |
| 검색·상태 필터·후속 연락 메모 | 없음 |
| 미응답 51번째 이후 고객 보기 | 없음. 오래된 순 50명만 표시하고 나머지는 건수로 표기 |
| 모바일 설문 현황 | 없음. 1024px 미만에서 데스크톱 안내만 표시 |
| 설문 생성 자체가 실패한 완료 건 추적 | 미응답 목록에 포함되지 않음. 접수 상세에서는 미발송으로 표시 |

또한 화면의 **발송 건수는 실제 SMS 성공 건수가 아니라 생성된 설문 수**다. 따라서 Solapi 실패 건도 발송 분모에 들어간다. `SmsLog.SENT` 역시 제공자 요청 성공을 뜻하며, 휴대폰 수신 확인은 아니다.

관리자 설문 화면의 기존 3개 UI/API 테스트를 실행해 조회 전용 동작과 모바일 제한을 확인했다. `surveyAnalytics.ts`의 조회 조건 및 50건 제한, 관리자 접수 상세 응답도 코드로 대조했다.

현재 완료 API는 설문 생성과 SMS 발송을 기다리지 않는 비동기 호출이다. 영속 작업 큐·자동 재시도는 구현되어 있지 않으므로, 프로세스가 종료되는 경우까지 전달을 보장하는 구조는 아니다. 다음 개선의 우선순위는 발송 실패/미응답 구분, 재발송·링크 복사, 전체 대상 페이지 이동 및 모바일 조회다. 이번 요청에 따라 설문은 내부 검증과 현황 확인을 수행했다.

## 소개 수수료 로직

현재 계산 기준은 **고객이 설문에 직접 입력한 지불 금액 × 2% (원 미만 버림)**다. 추천 관계가 있고 양수 금액을 제출해야 적립된다. 은행 입금·PG 결제·업체 정산 확정과 연결되어 있지 않다. 사용자가 설명한 '추천 업체의 정산액 × 3%'와는 다르며, 이번 표시 개선은 요율이나 기존 적립 장부를 변경하지 않았다.

## 적용한 알 충전·대시보드 개선

- 업체·기사 대시보드 상단 소개 수수료는 지급 대기+지급 완료의 누적 합계 하나로 통합했다. 지급 상태별 내역은 상세 화면에 유지한다.
- 내 추천 현황의 색상 배지와 장식 아이콘을 없애고 이름·승인 상태·가입일·누적 수수료를 단순한 목록으로 정리했다.
- 양쪽 대시보드에 알 충전하기 버튼을 추가했다. 페이지는 `/partner/eggs/charge`, `/tech/eggs/charge`다.
- 1판=30알, 1알=1,000원. 최소 30알, 30알 단위이며 수량에 따라 금액을 표시한다.
- 관리자 설정의 알 충전 입금 계좌에서 은행명·계좌번호·예금주를 저장한다. `/admin/settings#egg-charge-account`.
- 양쪽 포털이 같은 설정을 읽으며, 계좌번호 복사와 입금자명 안내를 제공한다.
- 입금 확인 뒤 관리자가 기존 회원 상세의 알 크레딧 기능으로 지급한다. 자동 입금 확인이나 온라인 결제는 구현 범위에 포함하지 않았다.
- 관리자 지급 API와 DB 충전 함수에서도 30알 단위를 강제한다. 같은 충전 키 재요청은 중복 지급되지 않는다. 정정은 기존처럼 개별 알 단위로 가능하다.
- 계좌 세 항목을 전부 비우면 등록 해제된다. 일부 입력·잘못된 계좌번호는 저장하지 않는다. 조회 장애 시 이전 계좌를 숨기고 재시도를 안내한다.
- 실제 입금 계좌는 아직 미등록이다. 화면 검증에 사용한 가짜 계좌는 테스트 종료 후 복원했고 스크린샷 미리보기의 계좌는 브라우저 응답만 대체했다.

Prisma migration `20260910020000_egg_charge_account`는 AppSettings에 nullable TEXT 3개만 추가한다. 현재 로컬 개발 DB와 분리 테스트 DB 모두 적용했다.

## 검증 기록

- Playwright 관련 62개 시나리오 최종 통과: 고객 API 20, 설문 연결 3, 관리자 설문 3, 알 충전 5, 포털 UI 25, API 목록 대조 6.
- Vitest DB 테스트 15개 통과: 알 장부 14, Solapi 실패 및 링크 보존 1.
- 변경 파일 ESLint, TypeScript, 프로덕션 빌드 통과.
- 실제 테스트 계정으로 업체·기사 로그인, 누적 수수료 값, 충전 페이지 이동 및 계좌 미등록 상태 확인.
- 320/390/768/1440px 가로 넘침 없음, 계좌 복사 성공. 충전 페이지 axe 검사 위반 0건, 브라우저 JS 오류 0건.
- 기존 빌드 경고: middleware 파일 규약 폐기 예정, uploads의 next.config import로 인한 광범위 파일 추적. 이번 기능의 빌드를 막지는 않음.
- 시각 증거: `charge-evidence/` 및 `charge-evidence/verification.json`.

로컬 확인: `http://localhost:3001`. 기존 `test_partner` / `test_tech`, 비밀번호 `Test1234!`. 사용자가 직접 진행한 배정 상태와 계정 잔액은 초기화하지 않았다.
